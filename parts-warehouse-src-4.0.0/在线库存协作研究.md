# 多人联网库存协作研究

更新时间：2026-08-28

## 2026-08-28 更新：Excel 日志与 JSON 事件分工

当前协作模型进一步明确为两层格式：

```text
本地库存/操作日志：标准 Excel
          <-> 明确的字段转换层
远端 Git 增量同步：独立 JSON 事件文件
```

一次业务操作只生成一条事件，事件的 `items[]` 保存该次操作的全部明细；不允许按明细拆成多个事件文件。客户端接收远端事件后，应先校验事件、定位目标子分类 Excel、按 `part_id` 或稳定快照信息找到目标行，再把数量变化写回标准 Excel，并将该事件记录为线上来源账单。转换、校验和撤回规则统一见 `Excel-JSON转换手册.md`。

日志 Excel 是本地业务归档，不是远端同步文件：它保存一次操作的完整明细，可用于账单展开、审计以及单项/批量/全体撤回。撤回应生成新的逆向业务事件，不删除原日志、不静默覆盖历史记录。

## 结论

`parts-warehouse` 可以增加多人联网协作，但“在线文档”不应直接作为严格库存扣减数据库。

推荐架构：

```text
多人浏览器/桌面客户端
          |
      Flask 业务服务
          |
  库存业务层 + 出入库流水 + 权限
          |
  在线数据提供商适配层
     |                 |
本地 Excel          在线多维表格/在线表格
```

第一阶段建议只做在线库存只读同步和搜索，确认账号、权限、字段和网络条件后，再增加入库/出库写入。

## 在线文档、在线表格、多维表格的区别

### 在线文档

适合：

- 仓库操作规范
- 采购说明
- 盘点备注
- 项目文档

不适合作为库存主数据，因为库存需要按物料记录查询、筛选、绑定 BOM、修改数量、记录流水和处理权限。

### 在线表格

例如 Microsoft Excel Online、Google Sheets：

- 与现有 Excel 文件兼容性较好。
- 适合多人查看和编辑二维表格。
- 有 API 可以读取和更新单元格、工作表、表格行列。
- 但行号不是稳定物料身份，必须增加稳定的 `part_id`。
- 文件级变更通知通常只能说明“文件变了”，不能直接告诉业务层哪一条库存发生了什么变化。
- 读取库存、计算新数量、写回数量不是天然的库存原子扣减事务。

### 多维表格

例如飞书多维表格、Airtable 类产品：

- 更接近结构化记录系统。
- 支持字段、记录 ID、筛选、视图和 API。
- 比普通在线文档更适合库存、BOM、采购和出入库流水。
- 仍然不能未经验证就当作具备数据库级行锁和库存扣减事务。

## 对当前项目的建议

### 当前不建议的做法

不要让多个客户端直接修改库存 Excel 中的数量列，然后由软件定时覆盖本地文件。这样会产生：

- 两人同时取料互相覆盖。
- Excel 行号变化导致 BOM 绑定错位。
- 无法可靠记录操作人和取料原因。
- 网络中断时本地和云端状态不一致。
- 云端表格和本地 Excel 双向修改形成冲突。

### 推荐数据模型

库存记录至少增加稳定字段：

```text
part_id             稳定物料编号
category            一级分类
subcat              子分类
name                名称/可检索型号
brand               品牌
package             封装
spec                规格
quantity            当前库存
location            库位
version             修改版本
updated_at          更新时间
updated_by          修改人
```

BOM 清单绑定 `part_id`，不能继续只依赖 Excel 行号。

出入库另建流水：

```text
operation_id        操作流水号
part_id             物料编号
operation           入库/出库/调整
quantity            数量
operator            操作人
timestamp           时间
reason              原因
client_request_id   防重复提交编号
```

### 推荐库存扣减流程

```text
客户端提交取出请求
  -> Flask 验证用户和权限
  -> 读取当前库存和 version
  -> 检查库存是否足够
  -> 写入出库流水
  -> 更新库存与 version
  -> 返回成功/冲突/库存不足
```

如果在线表格不提供可靠条件更新，应由 Flask 对关键 SKU 串行处理，或者把库存主数据放入 SQLite/PostgreSQL，把在线表格作为协作视图。

## 分阶段实施建议

### 第 1 阶段：只读在线库存

- 建测试云端表格/多维表格。
- 将当前 Excel 转换为云端记录。
- Flask 增加 `InventoryProvider` 接口。
- 实现在线搜索、分类查看、库存总览和低库存筛选。
- 不写入正式库存。

### 第 2 阶段：在线出入库流水

- 由 Flask 统一写入出入库流水。
- 记录操作人、时间、数量、原因和请求 ID。
- 加入重复提交保护。
- 验证两个客户端同时取料的结果。

### 第 3 阶段：BOM 清单联网调用

- BOM 清单 Excel 继续作为本地归档。
- 云端 BOM 记录使用稳定 `part_id` 绑定库存。
- 多人调用同一 BOM 时由 Flask 做实时库存检查。
- 缺料项、库存不足和绑定失效保持现有状态模型。

### 第 4 阶段：事件同步和多端部署

- 部署公网 HTTPS Flask 服务或 API 网关。
- 配置云端事件订阅/变更通知。
- 事件只作为刷新信号，服务端重新拉取记录并校验。
- 加入同步状态、失败重试和冲突处理。

## 方案 D：Git 仓库存储

Git 适合做“版本化文件仓库”，不适合直接充当多人实时库存服务。

### Git 适合的部分

- 保存源码、配置模板、分类定义和文档。
- 保存 BOM 清单 Excel 的历史版本。
- 保存库存快照，便于查看谁在什么时间提交了什么文件。
- 通过分支、Pull Request 和代码审查管理程序更新。
- 通过私有 Git 服务器或 GitHub/GitLab 进行远程备份。
- 可用 Git LFS 管理较大的二进制文件，但 LFS 仍然不是数据库或实时协作服务。

### Git 不适合直接承担的部分

- 多人同时在线查看最新库存状态。
- 多人同时取出并原子扣减同一物料。
- 按记录级别合并两个库存 Excel 修改。
- 防止两个客户端基于旧库存覆盖新库存。
- 提供库存权限、操作人和业务流水。
- 直接向浏览器推送库存变化。

当前项目的库存分类文件和 BOM 清单都是 `.xlsx`。XLSX 本质上是 ZIP 容器里的二进制/结构化文件，Git 通常只能判断整个文件发生变化，不能像文本代码一样可靠地合并两个用户对不同库存行的修改。两人同时改同一个 Excel 后，常见结果是冲突、覆盖，或者必须人工选择整份文件的一方。

### Git 作为库存备份层的可行架构

```text
Flask 库存业务服务
    |
    |-- 本地 Excel / SQLite 主数据
    |-- 每次入库/出库后生成操作日志
    |-- 自动提交库存快照到私有 Git 仓库
    |
远程 Git 仓库：版本历史、审计、备份、回滚
```

这种模式的优点是每次操作都有版本记录，缺点是 Git 提交不是实时多人事务，不能把“提交成功”当作“库存扣减成功”的业务确认。

### 如果坚持用 Git 做多人协作

最低要求：

- 使用私有仓库，不能把真实库存、供应商价格、采购凭证和用户信息推到公开仓库。
- 为每个物料增加稳定 `part_id`，不能使用 Excel 行号作为唯一定位。
- 禁止用户直接修改并推送库存数量文件；所有入库/出库必须经过 Flask API。
- Flask 对每个物料的操作串行化，写入出入库流水后再生成库存快照。
- Git 提交信息包含操作流水号、操作人和时间。
- 冲突时禁止自动覆盖，必须停止同步并提示人工处理。
- 使用 `.gitattributes`、统一换行规则和明确的 `.gitignore`。
- BOM 清单 Excel 可提交 Git 作为版本归档，但取出时必须读取业务服务中的实时库存。
- Git 远端认证使用 SSH key 或短期 token，凭据不得进入仓库。

### 推荐定位

```text
Git：版本控制、备份、审计、恢复
在线表格/多维表格：多人查看、协作编辑、信息共享
Flask + 数据库/串行业务层：库存扣减、权限、流水、一致性
```

如果团队只有低频操作、同一时刻只有一个人修改库存，Git + Excel 可以作为简化版备份方案；如果目标是真正的多人联网同时使用，Git 不应作为唯一存储后端。


- 多人查看库存：可行。
- 多人维护元器件信息：可行。
- 多人通过 Flask 统一入库/取出：可行，推荐。
- 多人直接在在线表格中改库存数量：可以做，但不建议作为关键流程。
- 在线文档直接承担严格库存扣减：不推荐。
- 当前项目最适合优先验证飞书多维表格；如果团队已有 Microsoft 365，则优先评估 SharePoint + Excel Online。
- 无论选择哪一种在线服务，都应先增加稳定 `part_id` 和出入库流水，再做多人写入。

## 方案 E：Git 作为库存变动事件仓库

用户提出的设想可以落地：所有参与者从同一个初始 `data` 快照开始，软件启动时只读取自己上次同步之后的新库存变动，再将本地变动上传到 Git。Git 不保存每次修改后的完整库存 Excel，而只保存追加式库存事件。

### 推荐目录

```text
inventory-sync-repo/
├── snapshot/
│   └── data.zip                 # 初始共同库存快照，低频更新
├── events/
│   ├── 2026/08/24/<event_id>.json
│   └── 2026/08/25/<event_id>.json
└── clients/
    └── README.md
```

每个库存变动使用一个独立 JSON 文件，不要让所有客户端同时追加同一个 JSONL 文件。独立文件可以让 Git 在多人提交时按文件合并，避免同一日志文件的文本冲突。

### 事件字段

```json
{
  "event_id": "UUID",
  "part_id": "稳定物料编号",
  "subcat": "仓库子分类",
  "operation": "withdraw",
  "delta": -3,
  "quantity_before": 10,
  "quantity_after": 7,
  "base_revision": "物料最后事件或快照版本",
  "client_request_id": "UUID",
  "actor": "参与者标识",
  "created_at": "UTC ISO-8601",
  "reason": "BOM清单取出"
}
```

`event_id` 用于防重复消费，`part_id` 用于稳定定位，不能使用 Excel 行号。现有 `activity_log.jsonl` 只有分类级汇总和数量净变化，不能直接作为同步事件，需要新增详细事件格式。

### 启动同步流程

```text
读取本地 sync_state.json
  -> git fetch / pull
  -> 找出上次 cursor 之后的事件文件
  -> 按确定顺序校验并应用事件
  -> 跳过已应用的 event_id
  -> 更新本地库存和 cursor
  -> 写入新的 sync_state
```

启动时只读取新增事件，不需要重复传输全部库存数据。首次安装或快照版本变化时，才重新获取完整快照。

### 最关键的限制

Git 可以合并两个事件文件，但 Git 本身不做库存事务。两台客户端都从库存 10 读到旧状态，同时取出 7 时，第二个事件重放会发现 `quantity_before=10` 与当前数量 3 不一致，必须标记为“同步冲突/未执行”，不能覆盖库存。

推荐由 Flask 同步服务负责校验当前版本和库存，Git 负责保存已接受事件、增量同步和审计历史。低频场景也可以让客户端直接 push 独立事件文件，但冲突必须进入待人工处理状态。

### 必须补充的保护

- 私有仓库；不上传 API key、密码、本地配置和公开库存敏感信息。
- UTC 时间、UUID、稳定 `part_id`。
- `sync_state.json` 记录快照版本、事件 cursor 和已应用事件。
- 事件应用幂等；push 重试复用原 `event_id`。
- 校验失败保留冲突记录，不静默丢弃。
- 远端不可用或事件格式错误时进入只读模式。
- BOM 绑定逐步从 `subcat + row + snapshot` 迁移到 `part_id`。
- Git commit 不是业务成功凭证，业务成功必须以事件被校验并接受为准。

#### 同一现场的功能内同步策略

根据本项目的实际使用方式，参与者通常在同一仓库现场操作，取料后再上传变动。因此不需要持续轮询 Git，也不需要把 Git 当作高并发数据库。

同步应嵌入仓库功能：

```text
进入库存浏览/元器件取出/BOM取出/入库
  -> 检测远端 Git 是否有新提交
  -> fetch 增量事件
  -> 重放未读取事件
  -> 刷新当前库存界面
  -> 用户执行本地操作
  -> 生成一条事件
  -> 上传事件到 Git
  -> 上传成功后标记本地已同步
```

如果用户只是停留在首页或使用设置、品牌库等不依赖实时库存的功能，不必触发同步。进入库存相关功能时同步即可，减少网络请求和无意义的全量读取。

“检测 Git 日志有没有更新”可以先用远程提交摘要完成：

```text
git fetch origin main
比较本地 sync_state.json 中的 last_commit 与 origin/main
相同：没有新增日志
不同：读取新增 events 文件并重放
```

本地操作上传时采用：

```text
本地保存库存变动
  -> 生成 event_id 唯一事件文件
  -> git pull/fetch 获取刚刚出现的其他事件
  -> 重放新增事件并刷新数量
  -> 写入自己的事件
  -> git add events/.../event_id.json
  -> git commit
  -> git push
```

这样即便两个人前后几乎同时取料，后上传者也会在上传前再次读取对方事件。按照用户的现场协作习惯，通常不会出现负库存；仍保留 `quantity_before` 校验作为异常保护，遇到不一致时提示“库存刚刚被其他参与者更新”，而不是静默覆盖。


当前 Windows 环境已经安装 Git，因此客户端可以使用“本地 Git 副本”方式，不必解析 GitHub 网页，也不必每次下载整个仓库。

#### 第一次使用

用户在软件设置中填写：

```text
同步仓库地址：Git HTTPS 或 SSH 地址
本地同步目录：程序数据目录之外的本地缓存目录
目标分支：main
```

软件执行一次：

```text
git clone --filter=blob:none --no-checkout <仓库地址> <本地同步目录>
git sparse-checkout set events snapshot/manifest.json
git checkout main
```

如果仓库规模很小，也可以普通 `git clone`。库存初始快照只在首次安装或快照版本变化时读取；日常启动不重复导入完整快照。

#### 日常启动

软件启动后由后台同步器执行：

```text
git -C <本地同步目录> fetch origin main
```

然后读取远端最新提交相对于本地游标新增的事件文件：

```text
git -C <本地同步目录> diff --name-only <last_commit>..origin/main -- events/
```

对每个新增的 `events/年/月/日/<event_id>.json`：

1. 校验 JSON 格式、事件签名/来源、`event_id`、`part_id` 和数量字段。
2. 检查本地 `sync_state.json`，已经应用过的 `event_id` 直接跳过。
3. 按提交顺序和事件时间重放未应用事件。
4. 检查 `base_revision` 或 `quantity_before`；不一致就生成冲突记录，不覆盖本地库存。
5. 全部成功后更新 `sync_state.json` 的 `last_commit` 和已应用事件集合。

`fetch` 只更新本地 Git 对象和远程分支指针，不会自动覆盖当前库存 Excel；库存更新由软件自己的事件重放逻辑完成。

#### 更简单的首版实现

首版可以不使用 `sparse-checkout`，直接使用 Python `subprocess` 调用 Git：

```python
subprocess.run(
    ["git", "-C", sync_dir, "fetch", "origin", "main"],
    check=True, capture_output=True, text=True,
)
```

然后用 Python `json` 读取事件文件，用 `git diff --name-only` 找出增量文件。不要用 `shell=True` 拼接用户输入的仓库地址或路径。

#### 认证方式

- 私有仓库 SSH：每台参与者配置自己的 SSH key，仓库只授予必要权限。
- 私有仓库 HTTPS：使用 Git Credential Manager 或系统凭据管理器，不把 token 写进仓库 URL、settings.json 或日志。
- 公共只读仓库：可以不配置凭据，但库存事件通常不应公开。
- 不建议软件内保存所有人的同一个 GitHub token。

#### 网络和失败处理

```text
启动同步
  -> 网络正常：fetch + 读取事件 + 重放
  -> 网络失败：使用本地已知库存，界面标记“未同步”，默认进入只读模式
  -> Git 仓库冲突：不自动 reset，不覆盖本地事件，进入同步冲突界面
  -> JSON 损坏：停止继续应用后续事件，保留错误文件和错误信息
```

启动同步不应阻塞页面无限等待。建议设置有限超时，先显示本地库存，后台完成同步；但在同步状态未知时不允许直接执行出库。

#### 为什么不用 GitHub API 作为首选

GitHub Contents/Commits API 也能读取文件，但需要自行处理分页、限流、认证、下载内容和提交游标；如果后续还要上传事件，仍需处理分支 SHA、并发 push 和冲突。直接使用本地 Git 客户端更适合“拉取提交、找增量文件、提交和推送”的完整流程。


现有项目已有共同 `data` 初始库存、追加操作日志和集中 Flask 操作入口；还缺少稳定 `part_id`、详细事件文件、同步游标、Git 重试和冲突界面。用户提出的“同一初始 data + Git 增量事件同步”可以作为正式开发方向，第一版应先做只读增量同步和事件重放，再做库存变动事件提交，不应上传完整 Excel 覆盖远端。


本文没有创建在线平台应用、申请凭据或连接正式库存，也没有修改正式库存数据。下一步应先确定目标平台和账号条件，再建立测试表做只读验证。
