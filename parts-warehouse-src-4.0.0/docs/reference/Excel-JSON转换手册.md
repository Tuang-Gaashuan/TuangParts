# Excel-JSON 转换手册

更新时间：2026-08-28
适用项目：`parts-warehouse`

## 1. 目的

本手册规定本项目中 Excel 与 JSON 的职责、字段映射和转换规则。

核心原则：

```text
Excel：本地库存和操作日志的业务归档格式
JSON：Git 远端增量事件的传输格式
```

Excel 与 JSON 不是同一种数据的两种随意写法。JSON 事件必须经过校验和定位后，才能影响本地库存 Excel；不能把远端 JSON 直接覆盖成一张 Excel，也不能用变化后的库存表反向猜测历史操作。

## 2. 文件模型

### 2.1 库存 Excel

当前库存采用“一级分类目录/子分类文件”的结构：

```text
data/
├── 电容/
│   └── 贴片电容(MLCC).xlsx
├── 电阻/
│   └── 贴片电阻.xlsx
└── ...
```

实际路径由 `warehouse/config.py` 的分类表和 `safe_filename()` 决定。不能仅凭用户输入拼接路径，必须通过子分类映射得到目标文件。

每个库存 Excel 的标准表头为：

```text
名称/型号 | 品牌 | 封装 | 数量 | 库位 | 子分类 | 规格参数 | 数据手册链接 | 备注
```

### 2.2 操作日志 Excel

后续日志库采用“一次业务操作一个 Excel 文件”：

```text
data/
└── 日志库/
    ├── 20260828-160000-ledger-xxxxxxxxxxxx-取出.xlsx
    ├── 20260828-170000-ledger-yyyyyyyyyyyy-入库.xlsx
    └── ...
```

文件名只用于人工浏览，真正身份以文件内的 `record_id`、`event_id` 或等价稳定编号为准。一次批量操作的全部物料明细必须放在同一个日志文件中，不按明细拆文件。

日志 Excel 的每一行使用标准库存字段，并增加操作快照字段：

```text
名称/型号 | 品牌 | 封装 | 数量 | 库位 | 子分类 | 规格参数 | 数据手册链接 | 备注 | part_id | delta | 数量变化前 | 数量变化后 | 明细状态
```

其中：

- `数量`：该明细操作涉及的数量，等于 `abs(delta)`。
- `delta`：库存变化量，入库为正，取出为负，调整可正可负。
- `数量变化前`、`数量变化后`：执行该明细前后的库存快照。
- `part_id`：稳定物料编号。没有稳定编号时，至少保存完整物料快照，不能只保存 Excel 行号。
- `明细状态`：例如“正常”“已撤回”“冲突”“跳过”。

## 3. Excel 到 JSON：生成远端事件

### 3.1 转换时机

本机操作完成并已写入库存 Excel 后，生成一条本地账本记录和一个待提交事件。事件提交成功后，日志记录状态改为 `submitted`。

预览、AI 解析、Excel 导入预览阶段只在内存中处理，不生成远端事件；只有用户最终确认写入后才生成事件。

### 3.2 一次操作对应一个 JSON

一次批量操作必须使用事件版本 2 格式：

```json
{
  "event_id": "evt-20260828-160000-a1b2c3d4",
  "event_version": 2,
  "operation": "withdraw",
  "username": "operator-1",
  "created_at": "2026-08-28T08:00:00Z",
  "reason": "BOM清单取出",
  "items": [
    {
      "part_id": "part-000123",
      "subcat": "贴片电阻",
      "name": "10K",
      "brand": "YAGEO",
      "package": "0805",
      "spec": "±1%",
      "delta": -100,
      "quantity_before": 500,
      "quantity_after": 400
    },
    {
      "part_id": "part-000456",
      "subcat": "贴片电容(MLCC)",
      "name": "100nF",
      "brand": "三星",
      "package": "0805",
      "spec": "50V",
      "delta": -50,
      "quantity_before": 300,
      "quantity_after": 250
    }
  ]
}
```

事件顶层字段：

| 字段 | 必须 | 说明 |
| --- | --- | --- |
| `event_id` | 是 | 全局唯一、幂等使用；也作为事件文件名的一部分 |
| `event_version` | 建议 | 当前批量格式为 `2` |
| `operation` | 是 | `restock` 入库、`withdraw` 取出、`adjust` 调整 |
| `username` | 是 | 操作人 |
| `created_at` | 是 | ISO-8601 时间，建议统一 UTC |
| `reason` | 否 | BOM、采购、盘点等原因 |
| `items` | 是 | 本次操作的全部明细数组，不能拆成多个事件 |

明细字段：

| 字段 | 必须 | 说明 |
| --- | --- | --- |
| `part_id` | 是 | 稳定定位物料；不得用 Excel 行号替代 |
| `subcat` | 是 | 目标子分类，用于定位库存 Excel |
| `name` | 建议 | 名称/型号快照 |
| `brand` | 建议 | 品牌快照 |
| `package` | 建议 | 封装快照 |
| `spec` | 建议 | 规格参数快照 |
| `delta` | 是 | 数量变化，入库正、取出负 |
| `quantity_before` | 强烈建议 | 写入前数量，用于并发冲突校验 |
| `quantity_after` | 强烈建议 | 本次操作预期写入后的数量 |

### 3.3 从日志 Excel 转成 JSON 的规则

1. 读取同一个日志 Excel 的所有有效明细行。
2. 从日志文件元数据或首行读取 `record_id`、操作人、操作动作、时间和原因。
3. 每一行转换为 `items[]` 中的一项。
4. `delta` 取日志中的数量变化字段；不得根据“入库/取出”文字临时猜符号。
5. 所有明细共用一个 `event_id`，生成一个 JSON 文件。
6. 生成 JSON 后做必填字段、数值和数量前后关系校验。
7. 事件文件写入 `events/YYYY/MM/DD/<event_id>.json`，再统一 `git add`、`commit`、`push`。

数量关系必须满足：

```text
quantity_after = quantity_before + delta
```

如果日志中只有操作数量而没有前后快照，允许生成事件，但该事件必须标记为需要同步时重新校验，不能假设远端一定可直接重放。

## 4. JSON 到 Excel：应用远端事件

### 4.1 总体流程

```text
git fetch
  -> 找到新增事件 JSON
  -> 校验事件格式
  -> 检查 event_id 是否已经应用
  -> 按 part_id 定位库存行
  -> 校验数量变化前的状态
  -> 写回库存 Excel
  -> 写入本地日志 Excel/账本
  -> 更新 sync_state.json
```

`git fetch` 只更新 Git 副本，不会自动覆盖本地库存 Excel。库存变化必须由应用层明确完成。

### 4.2 定位库存行

按以下优先级定位：

1. 使用 `part_id` 精确定位。
2. 如果旧数据没有 `part_id`，使用 `subcat + 完整物料快照` 匹配：名称/型号、品牌、封装、规格参数等。
3. 只允许把 Excel 行号作为临时提示，不能作为长期身份。
4. 找不到、找到多行或快照不一致时，事件进入冲突状态，不自动写入。

找到目标文件后，用 Excel 表头映射字段位置，不允许写死“第 4 列永远是数量”作为唯一依据。当前标准格式中数量通常是第 4 列，但表头才是可靠依据。

### 4.3 写入库存 Excel

对每个明细执行：

```text
当前数量 = Excel 目标行的数量
期望数量 = 当前数量 + delta
```

如果事件带有 `quantity_before`：

```text
当前数量 != quantity_before  -> 冲突，不写入
当前数量 == quantity_before  -> 继续
```

如果事件带有 `quantity_after`，还必须检查：

```text
quantity_after == quantity_before + delta
```

全部明细通过校验后，才保存本次涉及的库存 Excel。批量事件不能只成功写入一部分却把整条事件标记为已应用；发生异常时应保留冲突记录并停止提交游标。

### 4.4 找不到物料时

以下情况不得自动新建或覆盖物料：

- `part_id` 不存在，且快照无法唯一匹配。
- `subcat` 不属于当前分类配置。
- 事件明细缺少名称/型号等必要快照。
- 目标 Excel 文件损坏或表头不符合标准。
- 数量不是整数，或计算后出现负库存。

应保留原始事件、错误原因和处理状态，提示人工确认。修复后重新应用时仍使用原 `event_id`，不能为同一业务操作随意生成第二条事件。

## 5. 线上事件与本地日志的关系

远端事件应用成功后，应形成一条本地“线上来源”日志：

```text
origin = remote
sync_status = remote
```

这条日志只用于本机展示、审计和展开查看，不应再次进入待提交列表，否则会造成事件回传或重复扣减。

本机业务操作：

```text
origin = local
sync_status = pending -> submitted
```

`sync_state.json` 记录同步游标和已读 `event_id`。事件被标记为已读不等于库存一定成功写入；推荐只有在事件应用和本地日志落盘成功后，才推进业务应用状态。当前基础同步模块的读取游标与库存应用层需要保持这一边界。

## 6. 撤回规则

撤回不是删除历史文件，而是使用原日志明细生成一笔新的逆向操作。

### 6.1 逆向关系

| 原操作 | 原 `delta` | 撤回 `delta` |
| --- | ---: | ---: |
| 入库 `restock` | `+N` | `-N` |
| 取出 `withdraw` | `-N` | `+N` |
| 调整 `adjust` | `+N` 或 `-N` | 相反数 |

撤回事件应保存：

```json
{
  "operation": "adjust",
  "reason": "撤回 event-原事件编号",
  "items": [
    {
      "part_id": "part-000123",
      "delta": 100,
      "quantity_before": 400,
      "quantity_after": 500
    }
  ]
}
```

实际项目中也可以将撤回动作标记为 `withdraw_reversal` 或 `restock_reversal`，但必须在实现中统一一种枚举，并保留原事件编号。

### 6.2 三种撤回范围

- 单项撤回：读取原日志中的一行，只对该明细生成逆向变化；原日志该行标记“已撤回”。
- 多项撤回：读取同一日志中被选中的多行，生成一笔包含这些行的逆向业务操作；未选行保持原状态。
- 全体撤回：读取整份日志的全部未撤回明细，生成一笔完整逆向操作；原日志标记“已撤回”。

撤回前仍需做当前库存校验。若物料已被其他操作改变，撤回可能造成数量冲突或负库存；此时不得强行覆盖，必须显示冲突明细。

## 7. 兼容旧版单物料 JSON

旧版事件可能使用顶层单条格式：

```json
{
  "event_id": "evt-old-1",
  "part_id": "part-000123",
  "subcat": "贴片电阻",
  "operation": "withdraw",
  "delta": -3,
  "quantity_before": 10,
  "quantity_after": 7,
  "username": "operator-1",
  "created_at": "2026-08-28T08:00:00Z",
  "reason": "手动取出"
}
```

读取器可以兼容该格式，但内部应立即规范化为：

```text
一个事件对象
  -> items = [原事件对象中的单条明细]
```

写出新事件时统一使用 `event_version=2` 和 `items[]`，不再生成新的旧版单条格式。

## 8. 安全与幂等

- JSON 使用 UTF-8，写出时保留中文，不使用带 BOM 的编码。
- `event_id` 必须唯一且文件名安全，只允许字母、数字、短横线和下划线。
- 重试上传使用原 `event_id`，不能重复制造新事件。
- 事件文件只放业务事件，不上传本地库存目录、API key、认证信息和 `sync_state.json`。
- Git 提交成功不等于库存业务成功；业务成功必须以事件校验、Excel 写入和日志落盘都成功为准。
- 同一批量事件的明细必须整体处理，禁止静默部分成功。
- 任何冲突都要保留原事件和错误原因，不能直接删除或跳过。

## 9. 最小验收用例

转换功能至少验证以下场景：

1. 一份包含 3 行明细的日志 Excel 生成 1 个 JSON，且 JSON 只有一个 `event_id`、包含 3 个 `items`。
2. 入库、取出、调整的 `delta` 符号正确。
3. `quantity_before + delta = quantity_after` 校验能拦截错误事件。
4. 远端事件能按 `part_id` 写回正确的子分类 Excel。
5. 相同 `event_id` 重复读取不会再次改变库存。
6. 数量已被其他操作改变时进入冲突，不覆盖 Excel。
7. 单项、多项、全体撤回都只生成逆向变化，不删除原始日志。
8. 远端事件应用后的日志标记为 `origin=remote`，不会再次进入提交列表。
9. 一次事件中任一明细失败时，整条事件不推进为已应用。
10. 中文字段、中文文件名和空单元格在 Excel/JSON 往返后保持可读。

## 10. 当前实现边界

截至本手册更新时间，项目已有：

- 标准库存 Excel 的读写层 `warehouse/excel_store.py`。
- 结构化本地账本 `warehouse/ledger.py`，一笔操作集中保存 `details[]`。
- Git 事件读取、幂等游标和事件上传基础 `warehouse/git_sync.py`。
- 批量事件 `event_version=2` 的 `items[]` 上传格式。

以下部分应按本手册继续实现并测试：

- 日志库 Excel 的正式创建、读取和明细状态维护。
- Excel 日志到事件 JSON 的统一转换器。
- 远端 JSON 校验、定位并写回库存 Excel。
- 应用成功后的线上日志落盘和游标推进边界。
- 基于日志 Excel 的单项、多项、全体逆向撤回。
